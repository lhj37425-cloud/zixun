# 拆解说明

> 你正在帮用户拆解一个 GitHub 上的开源项目。只按这份说明做，不要另发明一套步骤。  
> 学习者是谁、怎么讲：先读 `prompts/profile.md`。  
> 文件格式以 `docs/TECH.md` 第 5.3、5.4 节为准。

## 你收到的任务长什么样

用户（或网页复制按钮）会说类似：

```text
请按照 prompts/dissect.md 拆解 https://github.com/作者/项目名
```

也可以只说「拆这个仓库」并给出地址。目标都一样：按下面四步，把结果写进本仓库的 `content/projects/`，并更新术语表。

## 开工前先弄清状态

1. 从 URL 取出 `作者/项目名`（repo）。
2. 算出文件夹名（slug）：全部小写，把 `/` 换成 `-`。  
   例：`LearnPrompt/ai-news-radar` → `learnprompt-ai-news-radar`。
3. 看 `content/projects/<slug>/` 在不在：
   - **不在**：这是新拆解 → 先建文件夹（见下一节），从第 1 步开始。
   - **已在**：这是「继续拆解」→ **不要重做已完成的步骤**；从第一个还没完成的步骤接着做。

### 怎么判断某一步完成了没有

对应文件存在，且全文里 **没有** `<!-- 待完成 -->` 这一行，就算完成。  
四个文件依次是：`01-overview.md`、`02-flows.md`、`03-run.md`、`04-qa.md`。

一次对话里可以连续做多步，但每做完一步就立刻：

1. 去掉该文件里的 `<!-- 待完成 -->`（写正式内容时不要留这个标记）。
2. 有新概念就写进 `content/glossary.md`。
3. 运行 `uv run dd build`，让网页进度更新。
4. 用一两句话告诉用户：这一步写好了、网页怎么打开看、下一步是什么。

四步都完成后，提醒用户可以复盘，把值得留的内容整理进 Obsidian（由用户自己决定，你不必代写 Obsidian 笔记，除非用户明确要求）。

## 建项目文件夹

用命令建（不要手搓，除非命令失败）：

```bash
uv run dd new-project https://github.com/作者/项目名
```

也支持 `作者/项目名`。它会建好 `content/projects/<slug>/`、`meta.json`（开始日期用北京时间当天），以及四个带着 `<!-- 待完成 -->` 的步骤模板。  
文件夹已经存在时命令会拒绝重复创建——这时直接从第一个未完成步骤接着做。

只要这个文件夹存在，项目线就不会再推荐它。

## 把对方的代码放到哪里

- 对方的仓库克隆（或下载）到本仓库的 **`sandbox/<slug>/`**，不要克隆进 `content/`。
- `sandbox/` 不提交到 git；里面只是给你读代码、跑命令用的工作副本。
- **跑对方的安装脚本之前**：先读一遍它会做什么，用中文向用户说明；拿不准就先问用户再执行。
- 需要 API Key 时：只放在对方项目或本机的本地环境变量 / `.env` 里，**绝不**写进 `content/`、文档或提交记录，也不在对话里完整打印密钥。

## 怎么讲解（全程遵守）

- 用**零基础能听懂**的中文：先讲「它在干什么」，再讲术语。
- 出现用户可能不懂的概念：在正文里用一句话解释，并写入术语表（见下文）。
- 不要大段粘贴英文 README；用你自己的话概括。
- 不要假装跑通：没执行的命令就写「尚未执行」；失败就如实写原因和你怎么处理的。
- 一级标题（如 `# 一页纸：…`）可以写，网页生成时会按产品约定处理；正文结构用二级标题组织。

## 第 1 步：一页纸 → `01-overview.md`

写清楚这四块（标题可照用）：

1. **解决谁的什么问题**
2. **为什么是现在**
3. **用户以前怎么解决**
4. **它好在哪**（三条左右短列表即可）

篇幅大约一页：让用户读完就知道「值不值得今天拆它」。依据来自仓库说明、Issues/Discussions 的摘要，以及你对代码目录的扫读——不要瞎编星标数或功能。

写完后去掉 `<!-- 待完成 -->`，`uv run dd build`。

---

## 第 2 步：两张流程图 → `02-flows.md`

必须有两节，每节里各有一个 ` ```mermaid ` 代码块：

1. **用户的操作流程**：人要点什么、确认什么、看到什么。
2. **agent（或系统）内部的流程**：程序/agent 内部怎么转（例如「想下一步 → 用工具 → 看结果」这类循环）。

图下面用几句中文对照两张图：用户眼里的一步，对应内部的哪一段。  
流程图用 `flowchart`（TD 或 LR 均可），节点文字用中文，尽量短。

写完后去掉 `<!-- 待完成 -->`，`uv run dd build`。

---

## 第 3 步：跑起来 → `03-run.md`

带着用户在**本机**把项目装好、跑通。建议结构：

1. **需要准备什么**（系统、Python/Node 版本、API Key、磁盘等）
2. **安装和运行的每一步**（每条命令单独列出，下面用中文解释它做什么）
3. **遇到的问题和解决办法**（没有就写「本次没有卡住」）
4. **跑起来之后看到了什么**（实际输出或界面的摘要）

命令默认在 `sandbox/<slug>/` 里执行；若必须装到别处，写明路径和原因。  
强依赖高端显卡或付费集群、本机实在跑不动时：写清卡在哪、最小可替代的验证方式（例如只跑测试、只起 CLI help），并征求用户是否继续硬扛。

写完后去掉 `<!-- 待完成 -->`，`uv run dd build`。

---

## 第 4 步：追问 → `04-qa.md`

这一步以**用户的问题**为主：

1. 请用户提出不懂的地方（代码、概念、和 FDE 相关的取舍等）。
2. 你回答，并把问答追加进 `04-qa.md` 的「问答记录」。
3. 把这次新学到的概念列入文末「这次学到的概念」，并同步进术语表。

如果用户暂时没有问题：可以先根据拆解过程列出 3～5 个「值得追问」的问题供选择，等用户挑了再写进记录；**不要伪造用户说过的话**。

当至少有一轮真实问答、且你认为这一步可以结束时，去掉 `<!-- 待完成 -->`，再 `uv run dd build`。用户若说「先记着，以后再问」，可暂时保留 `<!-- 待完成 -->`，把已有草稿留下。

---

## 新概念怎么写进术语表

文件：`content/glossary.md`。

1. 先搜索表里是否已有同名或同义术语；有则不必重复，可在「第一次出现」之外不改解释（除非原解释有误）。
2. 没有则追加一个二级标题，格式固定为：

```markdown
## 术语名
一两句零基础能懂的解释。
- 第一次出现：作者/项目名（拆解）
```

3. 「第一次出现」写清来自哪个拆解项目；不要指向已经删掉的示例。

---

## 安全与范围（拆解时也要守）

- 只改与本次拆解相关的 `content/projects/<slug>/`、`content/glossary.md`，以及 `sandbox/<slug>/` 工作副本。
- **不要**为了拆解去改今日一拆的产品代码、PRD，或提交 `.env`。
- 不要 `git push`；是否提交拆解文稿由用户决定。用户若要求提交，说明里写清改了哪些文件。
- 删除 `sandbox/` 或对方仓库里的文件前，先得到用户同意。

- [ ] 讲解是口语化中文，新概念进了术语表
- [ ] 第 2 步有两张可渲染的 Mermaid 图
